# M11: isolated build and immutable artifact admission

Implementation: build policy, manifest and log redaction in [`@embody/cloud-contracts` `build.ts`](../../packages/cloud-contracts/src/build.ts); build plan, admission, artifact records and retention in [`@embody/gateway` `build-admission.ts`](../../packages/gateway/src/build-admission.ts) with the [Cloud Build adapter](../../packages/gateway/src/cloud-build.ts); the recipe image in [`infra/mvp/builder`](../../infra/mvp/builder/); acceptance fixtures and cases in [`infra/mvp/m11`](../../infra/mvp/m11/). Decision: MD09 in [STATUS](./STATUS.md#decision-ledger).

M11 turns a verified M10 source into an admitted, digest-addressed image plus a trusted manifest. It does not deploy anything: the deployment controller (M12) calls `BuildAdmission.start`/`settle` from durable jobs, and M13 deploys only the admitted `imageReference`.

## Build contract (recipe `embody-node24-pnpm-v1`)

One pinned recipe; customer Dockerfiles, build images and package managers are not supported.

| Item | Value |
|---|---|
| Runtime | Node 24 (`node:24-bookworm-slim`, pinned by digest; 24.22.0 when pinned) |
| Package manager | pnpm 11.25.0; `packageManager` must be absent or exactly `pnpm@11.25.0` |
| Required files | `package.json` with `"type": "module"` and a `build` script; `pnpm-lock.yaml` (lockfile v9) |
| Build | `pnpm install --frozen-lockfile` (offline), then the project's `build` script |
| Layout | `tsc` output as generated by `create-embody-app`: `dist/embody.config.js` (default export `defineApp(...)`) and `dist/src/index.js` (the image's `CMD`) |
| Framework | `@embody/core` and `@embody/host` required; every `@embody/*` package must be the platform's bundled build (exact version and sha512 integrity) |
| Image | Pinned runtime base + the app tree at `/app`, uid 1000, `NODE_ENV=production`, production dependencies only |
| Limits | Whole build 600 s; sandbox 420 s; output 500 MiB; manifest 256 KiB; log 1 MiB (the rest is dropped) |
| Sandbox | No network, uid 1000, all capabilities dropped, `no-new-privileges`, 4 GiB memory (no swap), 512 processes, 2 CPUs, 4,096 open files |

`package.json` must not contain `workspaces`, `pnpm`, `overrides`, `resolutions`, `patchedDependencies` or bundled dependencies, and every dependency spec must be a registry version range (no `file:`, `link:`, `git`, URLs, `workspace:`, `catalog:`, `npm:` aliases or paths). The lockfile must have exactly one importer, match `package.json` exactly, and resolve every package from the registry with sha512 integrity: no tarball URLs, git, directories or links, and no lockfile overrides. Dependency build scripts follow pnpm's default (not run unless allowed; `better-sqlite3` stays unbuilt, which the PostgreSQL hosted runtime does not need). The root project's own lifecycle scripts do run, in the sandbox.

Hosted durable apps declare the event names they publish for other apps in `defineApp({ publishes: [...] })`. The gateway relay (M21) accepts only declared names.

## How a build runs

```text
gateway/controller (trusted)            Cloud Build default pool, us-central1, builder SA
  verifySubmissionSource ──► plan ──────► 1 prepare  (recipe image, network, NO customer code)
  signed GET (10 min, read signer)          fetch exact source → SHA-256 = verified digest
                                            re-validate + extract (M10 reader)
                                            input/lockfile policy, pnpm fetch --ignore-scripts
                                            lockfile audit, SBOM ─► step output (trusted)
                                        2 sandbox  (input image, docker create --network none, uid 1000, …)
                                            install, build script, manifest extraction
                                            (customer code; everything it writes is data)
                                        3 assemble (trusted, no RUN instruction)
                                            size bound, COPY tree into pinned runtime image
                                            manifest digest ─► step output (trusted)
                                          images: push <repo>/<ws>/<app>:<artifact>
                                          artifacts: manifest.json, sbom.json → outputs bucket
  settle: provider record + outputs ──► admit (digest reference) or reject (image deleted)
```

The sandbox starts from a per-build input image: the recipe image plus the source and dependency store, added by a platform Dockerfile with `COPY --chown` only (no `RUN`, no network). It returns the app tree and `manifest.json` by `docker cp`. (`docker cp -a` is not used: on Cloud Build it resolves the container user in the host's passwd file.) It never sees `/workspace`, the step environment (including the signed URL), `$BUILDER_OUTPUT` or the Docker socket, and with no network it cannot reach the metadata server, so it has no builder token.

## Admission (trusted code outside the build)

`decideAdmission` checks, in order, and the first failure is the outcome:

1. **Provenance.** The fields the platform sets in the provider's record of the build (steps' image, entrypoint, args, env and timeout; images; artifact location; service account; logs bucket; logging mode; build timeout) match the plan, compared by `configDigest` in their executed (substituted) form. The source URL is excluded from it. Fields the platform never sets (for example step `allowFailure`, `volumes` or `secretEnv`, `availableSecrets`, `options.pool`) are not compared: only the controller can create builds and it finds them by an unguessable artifact tag. Rejecting records that carry such fields is an M12 hardening item.
2. **Status.** `TIMEOUT` → `BUILD_TIMEOUT`; `INTERNAL_ERROR` → `DEPENDENCY_UNAVAILABLE` (retryable); a prepare-step policy code (`LOCKFILE_REJECTED`, `UNSUPPORTED_RUNTIME`, …) or `OUTPUT_LIMIT` is reported as such; anything else is `BUILD_FAILED`.
3. **Trusted step outputs.** The prepare output names the recipe and the exact verified source digest; the audit has no blocking advisory.
4. **Image.** Exactly one image, with the planned name, and a `sha256` digest reported by the provider (the build's own claims are never used). The admitted reference is `<repo>/<ws>/<app>@sha256:…`.
5. **Manifest and SBOM.** The objects in the outputs bucket hash to the digests in the trusted step outputs, so a manifest or SBOM substituted after the build is rejected (`MANIFEST_MISMATCH`). The manifest must parse as `BuildOutputSchema` and its catalog as `@embody/core` `appManifestSchema` (`MANIFEST_INVALID`).
6. **Profile and capabilities.** The submission's profile decides. Request-only: the sandbox preflight passed and the catalog has no workflows, subscriptions or declared publishes, else `UNSUPPORTED_PROFILE`. Durable: the durable preflight passed and every workflow has at most 50 steps, else `UNSUPPORTED_PROFILE`; `workflows`, `subscriptions` and `events` must each equal what the app actually has (`CAPABILITY_MISMATCH`).

The admitted `ArtifactManifest` (M11 manifest amendment for M19–M21) carries the profile, published event names, subscriptions, versioned workflow definitions and a digest of the catalog. `ReleaseManifest.artifact` (M13) embeds it. The preflight and catalog are produced by customer code, so they can only make admission stricter: runtime enforcement stays with the host (`assertRequestOnlyPlugins`/`assertDurablePlugins` at boot), M13 and M21.

A rejected artifact has no image reference or manifest, its public status has no digest, and its image and output objects are deleted immediately (logs are kept for the record's retention). Nothing is ever signed or executed with elevated credentials: the admission record in the platform database is the only thing M13 deploys from.

## Provenance, SBOM and vulnerability policy

- **Provenance:** the artifact record holds the builder identity, the provider build ID, the config digest and the build times. The provider record (Cloud Build `builds.get`, read with the controller's identity) is the source of truth; nothing the build writes about itself is trusted.
- **SBOM:** CycloneDX 1.5, generated by the trusted prepare step from the lockfile (name, version, purl, sha512 of each locked package), stored next to the manifest and bound by digest.
- **Vulnerabilities:** `pnpm audit` of the locked set against the public advisory database, run by the trusted prepare step. **Critical** advisories block admission (`VULNERABILITY_POLICY`); other severities are recorded. An unavailable advisory service fails the build as `DEPENDENCY_UNAVAILABLE`, which M12 may retry.
- Artifact Analysis container scanning is not enabled: it is billed per image and would scan the base image the platform already pins. Binary Authorization on Cloud Run is a recorded hardening option for M13.
- **Scans and provenance are not proof the code is harmless.** They reduce known-bad dependencies and bind the image to its source. Containment comes from the sandbox, the builder's identity and the runtime identity.

## Identities (MD09)

| Identity | Holds | Never holds |
|---|---|---|
| Builder (`<prefix>-builder`) | `artifactregistry.writer` on the builds repository; `artifactregistry.reader` on the platform repository (recipe image); `storage.objectCreator` plus `storage.legacyBucketReader` (bucket get and object listing, no object read; Cloud Build checks it can get artifact and log buckets) on the outputs bucket, so manifests and SBOMs are create-only; `storage.legacyBucketReader` and `storage.objectUser` on the separate logs bucket (Cloud Build requires bucket access for a user-specified logs bucket and rewrites the log object during the build) | source bucket access, any project role, Secret Manager, Cloud SQL, Cloud Run, IAM, `actAs` |
| Source read signer (`<prefix>-src-read`) | `storage.objectViewer` on the source bucket; signs only the builder's GET URL | write, delete, any other bucket |
| Controller (M12; the operator in the live run) | `cloudbuild.builds.create`/`get`/`cancel`, `actAs` on the builder only, `signBlob` on the read signer, delete on the builds repository and outputs bucket | `actAs` on any runtime identity for builds |

Tags in the builds repository are unique artifact IDs and are **never deployed**: admission binds the digest from the provider's own record, M13 deploys only `repo@sha256:…`, and the live suite repoints an admitted artifact's tag at another image to show that neither the record nor a fresh decision changes. The repository keeps mutable tags on purpose: Artifact Registry refuses to delete a tagged version in an immutable-tag repository (`FAILED_PRECONDITION`, observed live), which rejection cleanup and retention require. Platform images live in a separate repository the builder can only read.

**Residual risk:** a container escape on the build VM (a kernel or runc exploit) would reach the builder's token: push images to the builds repository, create objects in the outputs bucket, and **read** and rewrite every build's logs in the logs bucket (a confidentiality exposure of other tenants' build output; per-build log scoping is a hardening option). It cannot read sources, read secrets, reach databases or deploy, and the escaped build's own artifact is still bound to its own digest. Cloud Build runs each build on a fresh VM. The upgrade path is a private pool with no public egress plus a registry mirror for the prepare step (same per-minute price, more setup).

## Obligations for later tasks

- **M12** serializes each stage attempt (a lease) before calling `start`: two concurrent `start` calls for one attempt can both submit before either records a build ID (the loser's image is removed as an orphan, but it is wasted work).
- **M13** must not treat `manifest.appId`/`appVersion` as identity (they are customer claims); the platform app ID is the record's `appId`. The artifact keeps only `catalogDigest`: M13 re-reads the retained `manifest.json` and checks it against `manifestDigest` to obtain the catalog for promotion.
- **M15** serves `BuildAdmission.log` (bounded and redacted; an oversized log is truncated, never refused).

## Logs

Build logs are written by the provider to `gs://<logs bucket>/logs/<ws>/<app>/<artifact>/` (`GCS_ONLY`; no Cloud Logging ingestion), a bucket separate from the create-only outputs because Cloud Build rewrites the log object while a build runs. Logs are never admission inputs, so the builder's write access there cannot change what is admitted; an escaped build could alter or delete other builds' logs (diagnostics only). The sandbox's output is cut at 1 MiB. `BuildAdmission.log` returns at most 1 MiB with known platform values and secret-shaped strings (private keys, Google/GitHub/AWS/Slack/OpenAI-style tokens, bearer headers, signed URLs, database URLs) replaced by `[REDACTED]`. Builds receive no platform secrets; redaction is defense in depth. M15 serves logs to `deployment:read` callers.

## Retention and cleanup

| Record | Kept | Then |
|---|---|---|
| Admitted, unpinned | 30 days after the build (`inactiveReleaseRetentionDays`) | `purgeArtifacts`: CAS fence, delete image, outputs and logs, then the record |
| Admitted, pinned by a release (M13 sets `pinnedBy`) | while pinned | as above once unpinned |
| Rejected | image and outputs deleted at rejection; record and logs 14 days (`logRetentionDays`) | purged |
| Building | until settled; `settle` cancels a build still running 600 s + 10 min after creation and rejects it `BUILD_TIMEOUT`, and rejects a finished build it still cannot decide after that deadline `DEPENDENCY_UNAVAILABLE`. An abandoned `building` record is reclaimed by `purgeArtifacts` when it expires (cancelled, rejected `BUILD_TIMEOUT`, purged by a later sweep) | — |
| Orphaned image (no record references its digest) | until older than the build deadline + 1 hour | `cleanupOrphanedImages` deletes it |

M16 schedules the sweeps. `purgeArtifacts` pages by a (retainUntil, workspace, artifact) cursor and examines at most 10 × `limit` rows, so up to 10 × `limit` rows it skips or fails on (for example a version the registry refuses to delete) cannot starve the rest; they are retried on the next sweep. Each sweep starts at the head again, so more persistently failing rows than that would; M16 alerts on a non-zero `failed` count (or persists the cursor between sweeps). M12 should settle promptly and treat a `DEPENDENCY_UNAVAILABLE` rejection from an overdue settle as a new attempt, not a user error. Recommended backstops: a logs-bucket lifecycle rule deleting `logs/` after 15 days, and Artifact Registry cleanup policies that never delete tagged versions referenced by pinned artifacts. `cleanupOrphanedImages` keeps any image whose digest a record references or whose tag is a recorded artifact ID (a finished build not yet settled has only its tag); it lists the whole repository, so M16 should list by package at scale.

## Troubleshooting

| Code | Cause | Fix |
|---|---|---|
| `SOURCE_INVALID` | Upload not verified, expired, another app's, or its digest/size differs | Upload again with `embody source upload` |
| `INPUT_REJECTED` | Unsupported `package.json` field or dependency spec, no `build` script, not ESM | Use the scaffold's `package.json` shape; registry ranges only |
| `LOCKFILE_REJECTED` | Missing, stale or non-registry `pnpm-lock.yaml` | `pnpm install` with pnpm 11.25.0 and commit the lockfile |
| `UNSUPPORTED_RUNTIME` | Other pnpm version, or `@embody/*` not the platform build | Remove `packageManager` or pin `pnpm@11.25.0`; use the platform's framework version |
| `VULNERABILITY_POLICY` | A locked dependency has a critical advisory | Update it (`pnpm update`), redeploy |
| `BUILD_FAILED` | Install, build or extraction failed, or ran out of memory/processes | Read the deployment log; `pnpm build` must work without network after install |
| `BUILD_TIMEOUT` / `OUTPUT_LIMIT` | Over 420 s in the sandbox (the sandbox step reports `BUILD_TIMEOUT`), or output over 500 MiB | Smaller build; keep large assets out of `dist` |
| `MANIFEST_INVALID` | No `dist/embody.config.js` default export, an invalid catalog, or a manifest over 256 KiB (for example thousands of declared event names) | Keep the scaffold layout; export `defineApp(...)` |
| `UNSUPPORTED_PROFILE` / `CAPABILITY_MISMATCH` | App does not fit the declared profile, or declared flags differ from the app | Declare the durable profile with exactly the workflows/events/subscriptions the app has |
| `MANIFEST_MISMATCH` / `IMAGE_INVALID` / `PROVENANCE_INVALID` | Build outputs or record do not match the platform's build | Platform fault or tampering; report it, do not retry blindly |
| `DEPENDENCY_UNAVAILABLE` | Registry, advisory service or provider outage | Retry; M12 retries automatically |

## Runtime network controls (MD09)

Hosted apps keep Cloud Run's default internet egress and are contained by identity, not network: a per-app runtime service account with no project roles, app-only database roles, private ingress plus Cloud Run IAM, and per-app queues (qualified in M09). Apps may call external APIs. Deny-by-default egress (Direct VPC egress with firewall rules and Cloud NAT for allowed destinations) is the recorded upgrade path.
